# 应用及部署

应用可灵活承载游戏的各类功能模块，既支持单服务架构（如平台应用、测试应用），也支持多服务架构（如游服应用）。每个服务可配置多个独立容器，分别承担不同功能，并可根据需求通过公网或内网访问，满足多场景部署要求。

---

## 操作入口

在 Publisher 控制台左侧导航选择 **【服务端】** → **【应用】**，进入应用列表。  
可在此添加应用、更新部署、查看应用详情、配置自动开服与灰度发布等。  
当该游戏已切换为「云原生架构」时，服务端菜单会展示应用入口。

## 应用说明

### **单服务与多服务应用**

计算层的应用分两种类型：单服务应用 和 多服务应用。

- 单服务应用支持多Pod分布式部署。多服务应用内各服务不建议多Pod部署、一个服务对应一个Pod即可。
- 这两种应用都可以配置多个镜像仓库，方便该应用（映射 K8s 的 Svc/Pod）按进程切分子应用（映射 K8s 的 Container）合并部署；目前子应用不支持独立部署，仅支持在同一 Pod 内多容器部署。

应用的多服务场景对应的是游戏的多游服，其中每个服务有其对应的数字ID（工具内称为游服ID）。平台提供环境变量**SERVER_ID**供动态分配ID。自动开服占用ID数字范围 [1 ~ 9999]

- 单服务应用、对外对内各自只暴露一个访问地址（因为只有一个服务）。
- 多服务应用由于可以幂等地横向部署多个服务，对外对内有若干访问地址，即针对每个服务暴露一对访问地址。

多服务应用内横向部署是由外部事件驱动的。如游服应用、达到开服条件时系统触发、或者用户手动触发开服等。

![alt text](./doc-assets/multi-service-manual-create-auto-start.png)

- **内网**：不同应用间的内网通信可通过集群域名访问，即 `http://{服务名称}:{$PORT}`，示例：`http://open-platform:{$PORT}`。
- **外网**：外网访问应用需通过负载均衡域名 + 路径方式访问，即 `https://{SLB 域名}/{服务名称}`（含 wss），示例：`https://gamedemo-slb.stg.g123-cpp.com/open-platform`。


**示例**：

应用（如: **chat**）下的不同服务（如: **chat1**, **chat2**）、会对应下列不同资源：

- 公网访问路径（https://gamedemo-slb.stg.g123-cpp.com/chat $SERVER_ID，如
  - `https://gamedemo-slb.stg.g123-cpp.com/chat1 `
  - `https://gamedemo-slb.stg.g123-cpp.com/chat2`
- 内网访问路径（ http://chat $SERVER_ID:\[$port\]），如
  - `http://chat1:$PORT `
  - `http://chat2:$PORT`

## 创建应用

1. 在 **【服务端】** → **【应用】** 页点击 **「添加应用」**；
2. 选择应用类型：**游服** 或 **平台服**；
3. 填写应用名称：以英文字母开头，只能包含小写字母、数字或 -，且不能以 - 结尾
4. 别名：支持输入中文别名
5. 选择所需的容器及镜像仓库，创建应用时需指定镜像仓库，部署应用时指定镜像版本
6. 选择部署方式
   1. 应用支持为“停服更新”和“滚动更新”。如果你的应用无状态、请配置为“滚动更新”。
   2. 停服更新：先停止旧版本后启动新版本、推荐有状态应用使用（请确保内存数据落盘）
   3. 滚动更新：先启动新版本后停止旧版本、推荐无状态应用使用。
7. 是否启用公网地址，若未启动，则无法使用公网域名访问；未开启公网访问的应用，可在应用创建成功后开启
8. 点击确定，创建应用。
9. 创建完成后，在应用卡片或详情页点击 **「更新部署」**，
    1. 首次部署需配置资源大小（可直接使用系统提供的默认资源配置），填写环境变量、对外端口、健康检查等参数
10. 点击确定，完成应用部署，部署成功后，可进入运行中的 Pod 处理业务逻辑。

**应用部署参数**

- 此版本是否能回滚：
  - 镜像版本v1被选择后，下一次更新镜像版本，无法再选择v1 版本
- 环境变量
  - 环境变量是运行容器时传入应用程序的**键值对**，可以用来配置：数据库连接信息、配置路径等
- 启动命令 ENTRYPOINT：
  - 指容器启动时运行的主程序命令，它在容器生命周期内是**默认执行的命令**。
- 端口
  - 应用每个服务、只允许暴露一个端口对外。如果有多端口对外的需求、在无法通过额外部署应用解决的前提下，CP需自行做好路由转发。
- 健康检查说明
  - 所有待部署的容器、请妥善实现健康检查API、不建议无逻辑判断直接返回200。该API是用来给集群同时做liveness和readiness检测的。
  - **liveness**: 该检测不通过、集群认为该服务已死、会尝试重启服务。
  - **readiness**: 该检测通过后、集群认为服务已经正常运行、开始给该服务导流。
  - 集群支持4种健康检测类型、请根据服务端架构自行选择。
    - **httpGet**
      - **原理**：通过发送 HTTP 请求到容器内部的某个端口和路径，返回状态码 200\~399 视为健康。
      - **适用场景**：服务提供 HTTP 接口，如 Web 服务、API 服务。
    - **exec**
      - **原理**：在容器内执行一条命令，命令返回码为 0 认为健康，非零为不健康。
      - **适用场景**：应用没有 HTTP 接口，但可以通过命令判断状态。
    - **tcpSocket**
      - **原理**：通过 TCP 检查端口是否能连通，连通即健康。
      - **适用场景**：非 HTTP 协议服务，如数据库、Socket 服务等。
    - **grpc**
      - **原理**：使用 gRPC 调用指定服务的方法，返回成功即健康。
      - **适用场景**：gRPC 服务，例如微服务通信基于 gRPC。
- preStop 
  - 用于在容器终止之前执行特定的操作。它允许你在容器完全停止之前运行一个命令或发送一个 HTTP 请求，从而确保资源被正确清理或状态被妥善保存。
    - **用途**：
      - 在容器终止之前执行清理操作，例如关闭数据库连接、保存状态或释放资源。
      - 避免数据丢失或不一致。
    - `exec` **类型** 适用于在容器内直接运行命令进行清理。
    - `http` **类型** 适用于通过 HTTP 请求调用容器内的 API 进行清理。

**应用高级配置**
- 开启多副本或HPA
  - 应用副本数：如果你的应用支持分布式部署，可开启多副本，最多支持10副本。
  - HPA：如果你的应用需要根据 **CPU/内存等监控指标** 自动扩缩容 Pod，可开启HPA。
- 标签：标签用于给服务加上“标识”，便于 **分类、筛选、批量操作**。

## 应用常用操作说明

### 登入pod

应用部署成功后，支持登入pod。使用此操作需要在增加新应用时勾选【允许登录pod】（已默认勾选），在应用卡片界面快捷操作【登入Pod】，或者进入服务详情界面选择【登入Pod】后可启用Pod控制台，用于debug等操作。

![alt text](./doc-assets/login-pod.png)

### 更新部署

点击【应用卡片-更新部署】，可修改镜像版本、容器参数，对应用进行更新。容器镜像仓库不可更改，只能改镜像版本。

### 资源配置

- 可修改应用的CPU和内存配置
  - 游服：修改资源配置会在下次开服的服务资源配置生效。仅对下次开服生效，不会影响已创建的服务；若需修改已创建服务的资源配置，可至”服务列表”页逐一修改；
  - 平台服务/测试服务：对应用的资源配置进行修改，可立即生效，或下次部署时生效
    - 立即生效：pod会立即重建，需确保不影响正常业务运行
    - 下次部署时生效：应用有部署行为（含标签立即生效、镜像修改立即生效、应用更新部署）时资源修改生效

### 编辑服务

- 仅游服可操作，游服详情页可以查看已经开服的服务信息，可对服务进行编辑/重启/停止/删除的操作；支持修改服务资源配置
- 点击服务名称，展开详情，可查看服务下的容器状态，或登入容器执行操作

### 分组管理

- 【详情-部署管理-分组管理】tab,可对游服服务进行分组管理，通过分组，可实现分组部署不同版本游服、适用于先行服、监修服等A/B运行场景。
- 点击【创建分组】，可根据游服ID进行分组，一个游服ID只能在一个分组，请自行做好组别规划。


### 变更记录

【详情-部署管理-变更记录】,可查看应用每次更新部署的时间、镜像版本、对外端口等参数


### 文件下载

## 自动开服

* 游服类型APP需支持、在特定开服策略（如创角人数 createRole 5000人、付费人数 paidUsers 3000人）下的自动部署与开服功能。
* 平台定时查询客户端流量（如创角人数、付费人数）是否达到开服策略定义（如创角5000人）时，会触发“自动开服”操作。
  * 若开服策略配置了多条，开服策略将按配置表中自上而下的顺序依次应用并循环；
  * 一条开服策略有多个条件，满足其一则触发开服
  * 自动开服触发后，会通知游戏将用户导流至游服N（导流服）

### 需实现的接口

#### 部署通知 API{#api-new-server}

当**游服APP**完成`1服`部署并首次开启自动开服功能时、系统会主动发起针对`2服`的部署API调用。此时`1服`为**导流服**、`2服`为**预备服**（完成部署、等待开服）

- Webhook

必须是 https 接口、请在Publisher内记入 `{ Webhook }` 

- Authorization

平台调用该 `{ Webhook }` 时会使用、请在Publisher内记入 `{ Token }`

- Request

> 当自动开服策略 **不包含创角人数**（如按付费人数或者定时开服等）时、请求中的 **serverUsers** 字段将默认传入：**0**

```json
{
  "actionId": string         // 操作的TraceID, publisher会用该TraceID来追踪这次操作的状态
  "serverUsers": number      // 新服配置的创角人数或0
  "serverId": number         // 当前请求开第几个服
  "newServerNames": []string // 游服类型APP下的Pod名称、即{游服APP名称}{serverId}
  "callbackToken": string    // 调用平台回调API时需要回传该Token
}
```

- Response

```json
{
  "message": string
}
```

| HttpStatusCode | Description                                                           |
| -------------- | --------------------------------------------------------------------- |
| 200            | OK. 如果webhook同步执行，耗时不长，可直接返回200无需回调平台                  |
| 202            | Accept. 如果该webhook需要异步执行，返回202. 完成后调用平台的开服回调 API      |
| 403            | No Permission. 当Token不正确时                                          |
| 422            | 请求不能执行，请返回 message                                             |

*示例*

- Webhook

`https://appid-slb.stg.g123-cpp.com/center/new_server`

- Authorization

Token: `test_g123_token1234`

- Request

POST `/center/new_server`<br />
Host: `https://appid-slb.stg.g123-cpp.com`<br />
Authorization: `test_g123_token1234`

```json
{
  "actionId": "1000",
  "serverUsers": 5000,            // 新服配置5000创角
  "serverId": 2,                  // 新服为2服
  "newServerNames": ["game2"]     // 游服类型APP名称为game
  "callbackToken": "^6Q%j0kZ74S"  // 调用平台回调API时需要
}
```

### 业务场景

下面以 **N** 表示当前导流服 ID。涉及的 API 编号统一约定如下（详见上文接口定义）：

| 编号 | 名称 | 调用方向 |
| --- | --- | --- |
| ① | 游戏内创角查询 | 平台 → 游戏（可选，需开启「保护机制」） |
| ② | 客户端创角埋点查询 | 平台内部（默认） |
| ③ | [开服通知](#api-open-server) | 平台 → 游戏 |
| ④ | [开服回调](#api-open-server-callback) | 游戏 → 平台 |
| ⑤ | [部署通知](#api-new-server) | 平台 → 游戏 |
| ⑥ | [部署回调](#api-new-server-callback) | 游戏 → 平台 |

通用开服步骤（按需启用）：

| 步骤 | 动作 | 涉及 API |
| --- | --- | --- |
| 一 · 开服 | 通知 N 服可进入、导流到 N 服、钉钉通知结果 | ③ → ④ |
| 二 · 监控 | 监控 N 服运行数据 | — |
| 三 · 初始化下一服 | 通知游戏初始化 N+1 服（DB、配置等） | ⑤ → ⑥ |
| 四 · 部署下一服 | 平台自动 `$SERVER_ID + 1` 部署 N+1 服 | — |

开服触发条件统一通过 API ②（默认）或 API ①（启用保护机制时）查询创角/付费数据，下文不再赘述。

#### 场景一：工具内全部游服启用自动开服

适用滚动开服。**完整执行步骤一 ~ 四**，平台自动完成预备服部署。

![alt text](./doc-assets/auto-example.jpg)

#### 场景二：工具内不部署游服，仅判定开服条件

适用 CP 自行管理逻辑服 / 物理服的场景，**不执行步骤四**：

- 虚拟机部署：执行步骤一、二、三
- 容器部署：执行步骤一、二、三

#### 场景三：调整自动开服的关联应用

启用自动开服并完成多次开服后调整应用，已离场应用的服务 ID 不会回补，会出现**不连续**。下表设：调整前导流服为 `N-1`，调整后再次开服时导流服为 `M-1`（`M > N`）。

**情况 A：先移除应用 A，多次开服后再加回**

| 应用 | 导流服 | 预备服 | 应用内服务 ID 序列 |
| --- | --- | --- | --- |
| A（移除期间） | N-1 → N | N | 【1】…【N】 |
| A（重新加入后开服） | — | M+1 | 【1】…【N】、【M+1】（不连续） |
| B（全程在列） | N → M → M+1 | N+1 → M+1 | 连续 |

**情况 B：移除应用 A，新增全新应用 C**

| 应用 | 导流服 | 预备服 | 应用内服务 ID 序列 |
| --- | --- | --- | --- |
| A（已移除） | N-1 | N | 【1】…【N】 |
| B（保留） | N → N+1 | N+1 → N+2 | 连续 |
| C（新增首次开服） | — | N+1 | 【1】、【N+1】（不连续） |

### AI 开服（支持多导流服场景）

#### 什么是 AI 开服

AI agent 根据综合业务数据（活动效果、留存预测、社交热度等）主动判断是否需要开新服，并自动执行开服流程。

与原有自动开服不同，AI 开服支持**按维度独立开服**，同一游戏可以同时存在多个导流服，每个导流服对应一组维度标签。CP 可根据不同维度，将游戏用户引导至不同的导流服。目前支持

#### 多维度并行开服模型

```
                    Publisher 平台
                    ┌──────────────────────────────┐
   AI 触发 lang=en, country=US  │  导流服 3 (en/US)     ←── 北美英文用户入口   │
   AI 触发 lang=ja, country=JP  │  导流服 4 (ja/JP)     ←── 日本用户入口      │
   AI 触发 lang=default         │  导流服 5 (default)   ←── 其他用户入口      │
                                 │  预备服 6 (不带标签，等待下轮)  │
                    └──────────────────────────────┘
```

**关键概念**：

- **分区维度**：标识一组导流服的定位维度，包含语种（lang）、国家/地区（country）、货币（currency）等
- **导流服**：当前正在接收新玩家的服，不同维度的导流服互不影响，并行运行
- **预备服**：为下一轮开服准备，不带维度标签

AI agent 可以多次触发开服，每次传入不同的维度组合，从而为不同用户群体开设独立的导流服。CP 根据玩家的语言、地区、货币等信息，将玩家引导至对应导流服。

#### Webhook Body 变更

AI 开服触发后，Publisher 调用 CP 的**开服通知接口**（`openServerNotify`）时，请求 body 新增维度字段：

**原有字段（不变）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `appId` | `string` | 游戏 ID |
| `actionId` | `string` | 本次开服动作唯一标识 |
| `serverId` | `int` | 新开的服号 |
| `serverUsers` | `int` | 该服用户上限 |
| `newServerNames` | `string[]` | 新服关联的应用名称列表 |
| `callbackToken` | `string` | 回调凭证 |

**新增字段**：

| 字段 | 类型 | 说明 | 当前状态 |
|------|------|------|----------|
| `lang` | `string`（可选） | 语种标识 | **已支持** |
| `country` | `string`（可选） | 国家/地区代码 | 规划中 |
| `currency` | `string`（可选） | 货币代码 | 规划中 |

**字段取值**：

| 字段 | 取值示例 | 说明 |
|------|----------|------|
| `lang` | `ja`、`en`、`zh-CN`、`zh-TW`、`fre`、空或 `default` | 语种标识，`default` 表示全球服 |
| `country` | `JP`、`US`、`CA` | ISO 3166-1 Alpha-2 国家/地区代码 |
| `currency` | `JPY`、`USD`、`GBP` | ISO 4217 货币代码 |

> **注意**：`country` 和 `currency` 字段当前尚未支持，后续版本会逐步开放。CP 可提前预留处理逻辑。

#### CP 需要做的适配

**1. 解析维度字段**

CP 后端在处理 `openServerNotify` 回调时，解析 `lang` 等维度字段，将导流服与维度绑定：

- CP 可维护一份 `维度 → serverId` 的映射表
- 玩家登录或创角时，根据玩家的语言、地区、货币等信息，路由到对应导流服
- 维度可组合使用，例如 `lang=en` + `country=US` 表示北美英文服

**2. 回调接口不变**

CP 的回调接口（`open_server/callback`、`new_server/callback`）无需改动，保持原有回调格式即可。

> **向下兼容**：所有维度字段均为可选。策略模式/人工触发的开服不带这些字段，CP 按"全球服"处理即可。

#### 示例：多维度开服流程

```
时间线：

1. AI 触发 lang=default → 开服通知 serverId=3
   → CP 记录：全球服导流服 = 3

2. AI 触发 lang=en, country=US → 开服通知 serverId=4
   → CP 记录：北美英文服导流服 = 4

3. AI 触发 lang=ja, country=JP → 开服通知 serverId=5
   → CP 记录：日文服导流服 = 5

4. 玩家登录时：
   → 检测玩家语言、地区等信息
   → en + US → 导流服 4
   → ja + JP → 导流服 5
   → 其他    → 导流服 3
```

#### 钉钉通知

AI 触发的开服成功后，运营群会收到如下格式的钉钉通知：

```
AI触发
游服N服开服成功
语种：英文服
原因：付费人数超目标
开启以下服务：
- game-server
```

## 多副本和HPA

### 前提条件

开启多副本或HPA，需确保满足以下条件：
- 架构服务无状态化：避免将用户状态、缓存、事务等保存在本地内存，应放入 Redis、数据库等中心服务。
- 接口幂等性保障：关键操作（如下单、支付）必须可重复执行，防止副本间重复处理。
- 共享资源使用中心组件：避免写入本地文件，使用对象存储、Redis、数据库替代共享目录。
- 连接池容量合理配置：多副本将放大连接数，需控制数据库/Redis 的连接池上限。
- 缓存一致性与穿透保护：处理好缓存一致性与穿透（如使用分布式锁、本地兜底）。
- 日志集中收集：日志应输出到 stdout，并通过日志组件（如 FluentBit）集中采集。
- 健康检查配置完整：配置 readinessProbe，确保服务就绪才接流量。
- 定时任务单点执行：多副本下避免重复执行定时任务，可使用 Job 或选主机制。
- 统一会话管理：避免本地 session，建议使用 JWT 或 Redis 存储用户登录态。
- 限流策略支持多副本：使用 Redis、服务网格等方案替代本地限流逻辑。

### 操作步骤

1. 在【应用-添加应用】或【应用详情-高级配置】，开启多副本或弹性扩缩容（HPA）
   1. **设置副本数**：输入 1~10，默认 1。
   2. **开启 HPA**：
      * 设置 **最小副本数**（1~10）
      * 设置 **最大副本数**（2~10）
      * 设置监控指标（CPU 或内存阈值），监控项之间为 ”或”关系，任一指标达到就会触发；推荐值： 70%-80%
2. 点击 **保存**。

**生效规则**
- HPA 开启后，手动设置的副本数将失效。
- 运行中修改，立即生效，可能会根据设置的指标和副本数进行扩缩容操作，在现有基础上增减Pod；停止状态修改，下次部署生效。

**触发规则**
- 触发条件为“或”关系：当 CPU 或内存 的平均利用率 任一项高于目标值（如 80%） 时，系统会评估并逐步扩容，以降低负载，使利用率稳定在目标范围内。若CPU负载过高，会连续触发扩容。
- 当 平均利用率低于目标值 时，系统会评估是否缩容。若缩容后剩余实例的平均利用率仍将高于目标值，则不会缩容。
- HPA 会持续调整实例数量，使平均资源利用率保持在设定目标值附近，而非超过即扩容。

## 应用标签

- 可为服务添加多个自定义标签（key-value）。
- 标签用于应用分组、检索、环境识别等。

### 操作步骤

1. 在【应用-添加应用】或【应用详情-高级配置】中，进入 **标签**。
2. 输入标签：
   - **Key**：1\~63 个字符，支持字母、数字、`-`、`_`、`.`。
   - **Value**：≤63 个字符，支持字母、数字、`-`、`_`、`.`。
3. 点击 **新增标签** 可继续添加，或点击 **删除图标** 移除。
4. 保存后，修改将在 **下次部署生效**。

**注意事项**

- 标签不可重复，若 key 已存在，将覆盖原值。
- 部分 key 为平台保留（如 `app`、`serverId`），禁止使用。
- 自定义添加的标签将统一加前缀 `{appid_}`。
- 部署后自动加到应用对应的deployment和service上

### 批量设置标签

1. 在【应用-设置标签】，选择需要设置标签的应用，
2. 点击新增标签，输入标签：
   - **Key**：1\~63 个字符，支持字母、数字、`-`、`_`、`.`。
   - **Value**：≤63 个字符，支持字母、数字、`-`、`_`、`.`。
3. 点击 **添加至应用** ，标签将批量添加到所选应用中；
4. 在列表标签预览页，点击删除，可逐个删除各个应用的标签，或点击清空，清空应用所有自定义标签（平台标签不清空）
5. 保存后，修改将在 **下次部署生效**。

## 部署计划

批量部署应用功能用于统一管理多个应用的更新或停止操作，通过创建部署计划可以实现：

* 一键部署多个应用
* 设置部署顺序（并行/串行/混合）
* 支持立即执行或稍后执行
* 查看部署执行结果和历史记录

### 创建部署计划

1. 在左侧导航栏选择 **应用 → 部署计划**
2. 点击 **“添加部署计划”**
   1. **部署计划名称**：输入名称（1-24字符，可中英文、数字、大小写字母及 `- _ .`）
   2. **部署详情**：输入描述（1-500字符，可中英文、标点、空格、换行）
   3. **操作类型**：选择 **更新服务** 或 **停止服务**
   4. **部署顺序**：选择 **并行**、**串行** 或 **混合**
   5. 点击 **“添加应用”**
      1. 选择要操作的应用
      2. 如果选择 **更新服务**：
         * 设置要更新的镜像版本
         * 选择是否支持回滚
   6. 支持调整应用执行顺序

**保存与执行**

点击 **保存**，稍后在列表中点击 **执行** 并确认

### 执行部署

1. 列表页点击 **执行**
2. 弹出确认弹窗，显示差异信息：资源配置、镜像版本、标签、Headless 状态
3. 点击 **确认** 开始部署

> **未执行**：可编辑或删除计划
> 
> **执行中**：可取消或暂停计划，（仅对未执行任务生效，已开始部署的应用无法暂停）
> 
> **暂停**：可继续执行剩余任务
> 
> **失败/部分失败**：可从失败位置重试

### 查看部署详情

点击部署计划名称，可查看：

* 参与部署的应用
* 部署结果（成功 / 失败 / 取消 / 执行中）
* 执行记录（状态、开始/结束时间、错误日志）
